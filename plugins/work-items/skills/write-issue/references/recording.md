# Work-item recording

Work Items owns classification, recording facts, reconciliation, persistence and verified closure.
Repositories that record work select this package and an authorized provider. Missing installation
or provider selection blocks recording; it never selects a Markdown register or another backend.
Existing historical records and substantial design plans remain source evidence, not a live fallback queue.

## Select the provider

Load `work-items:manage` and run its `scripts/work_item.py provider --root <checkout>` command using
its actual installed directory, with `python -B` on Windows or `python3 -B` on Linux/macOS. The command
resolves Git's source primary checkout and returns the explicit `.problem-records.json` provider.
Load that qualified provider skill and use its shipped commands with the returned primary root.
Installation does not adopt a tracker. Never create or change selection merely to record an observation.
Respect explicit employer and repository scope; credentials and native field/state policy remain with
the provider. Never redirect employer facts to a personal tracker after a selection or transport failure.

If the provider is unavailable, malformed or offline, retain the actual unsent facts in the current
task or goal, name the blocked operation, resolver and observable resume condition, then continue
independent authorized work. Pending input is not a persisted item or a new canonical backlog.

## Reconcile and persist

Before creation, use the provider's list/read commands to reconcile cause, requested outcome, source
owner, legacy identities, goals, sessions and repair links. Repeated observations update the same
canonical item. Similar symptoms or unknown causes do not establish duplicates. A known repair keeps
one owner; link a distinct related incident or compromise without duplicating that repair.

Obtain the kind's schema/template, fill it from observed facts, validate and preview, and let the
provider render its managed format. Keep unknown facts explicit. Persist one stable request identity
before submission and reuse it after uncertain outcomes; never blindly repeat a create. Read back
identity, kind and content before reporting success. Read before updates, use the provider's revision
or expected-hash checks, and coordinate one actual writer. Use notes to preserve earlier evidence.

Use provider list/read for live backlog, including items with no local plan. Source plans, review
artifacts and curated roadmaps link to canonical item identities and retain design and verification
evidence; they do not become a second live queue. Recording alone grants no implementation, credential,
publication, scheduling or dispatch authority. Continue an existing authorized lifecycle only within
its recorded scope; recording a new item does not start that lifecycle.

## Required facts and retention

Every item has a precise kind, substantive title/summary, requested outcome or concrete observation,
source owner, supporting evidence and an observable acceptance or resolution condition. Preserve
priority, dependencies, state, source links and legacy identities when supplied; do not invent them.
A bug is faulty software behavior; a mistake is an observed agent/process error; debt is an intentional
shortcut or deferral; a feature describes new/changed behavior; a task names concrete work.

Bug, mistake and debt records additionally state observed date, confirmed cause or explicit unknown,
impact and justified priority, owning component/repository, current state, repair link, next action
and actual verification evidence. Use the provider's supported states and canonical identity.
A blocked or deferred record names its reason, blocker class (`capability`, `dependency`, `conflict`
or `capacity`), resolver and observable resume condition. A conflict names the other owner and scope.

Close only after the item's own acceptance/resolution condition has observed evidence. Preserve the
canonical record, learning history and old links under the provider's retention policy. A linked
mistake resolves only when its prevention condition passes. Preserve existing remote IDs and request
receipts throughout caller migration; removing obsolete code does not authorize deleting user records.
